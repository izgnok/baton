# 공유 사본·채팅으로 레포 정하기 설계

작성 2026-11-27. 기존 설계(`2026-11-26-claude-rooms-design.md`)의 결정 5·16~18·28·38 을 이 문서 기준으로 바꾸고, 결정 40 을 이 내용으로 고쳐 쓴다.

| U15 | 같은 레포를 서로 다른 기준 브랜치로 동시에 여러 개 둘 수 있다(방 레포는 id 로 구분, 사본도 id 별 worktree, 원본은 함께 빌려 씀). 같은 레포가 둘 이상이면 이름에 기준 브랜치를 붙여 구분한다(예 `insight · develop`) |
| U16 | 작업 브랜치(자식)가 나오는 곳에는 항상 기준 브랜치(부모)를 함께 보여 준다 — 레포 카드 `release/15.7.0 → feature/X`, 채팅 기록 "… feature/X로 정했어요 (release/15.7.0에서)", Claude 안내문 "기준 … → 작업 …". push 뒤 작업 브랜치가 새 기준이 되어도 처음 갈라진 부모(`origin_branch`)는 툴팁에 남긴다 |

## 2. 모델

방 레포 하나 = `{ name, remoteUrl, baseBranch, workBranch }`
- `baseBranch`: 원격에 있어야 한다. 사본의 출발점이자, 남이 push 한 것을 따라가는 기준.
- `workBranch`: 이름만 있다(원격에 없어도 됨). 비어 있으면 기준 브랜치에 바로 push 하는 것으로 본다.
- 서버는 레포마다 **코드 상태**를 보관한다: `{ baseCommit, snapshot(커밋 id), bundle(파일), size, updatedBy, updatedAt }`. 아직 아무도 고치지 않았으면 비어 있다(= 기준 브랜치 그대로).

각자 맥: 원본(자동으로 찾은 같은 원격의 레포, 없으면 자동 clone) → 그 git 데이터를 빌려 쓰는 방 사본(`~/.claude-rooms/<방>/repos/<id>-<name>`, worktree, 항상 detached).

## 3. 흐름

### 3.1 레포 정하기 (채팅)

1. 사용자가 "insight 랑 mrs-integration-module 로 NMRS-23055 하자"처럼 말한다.
2. Claude 는 방 도구로 지금 방 레포를 보고, 요청한 사람 맥에서 찾은 레포 목록(이름·원격)에서 고른다. 기준 브랜치는 **그 레포의 코드를 읽거나 고쳐야 하는데 방에 기준 브랜치가 아직 없을 때만** 원격 브랜치 목록(`git_read branch -r`)을 보고 사용자에게 묻는다(U13). 이미 정해진 레포는 묻지 않고 그 기준으로 바로 일한다. 작업 브랜치 이름도 처음 정할 때만 제안하고 확인받는다.
3. 정해지면 방 도구로 설정한다. 서버가 방 상태를 바꿔 모두에게 알린다.

Claude 에게 주는 방 도구(기존 승인 MCP 서버 `rooms` 에 추가):
| 도구 | 하는 일 |
|---|---|
| `room_repos` | 방 레포 목록과 기준·작업 브랜치, 코드 상태 요약 |
| `local_repos` | 요청한 사람 맥에서 찾은 레포 목록(이름·원격 주소) |
| `room_set_repo` | 레포 추가 또는 기준·작업 브랜치 변경 `{ remoteUrl, name?, baseBranch, workBranch? }` |
| `room_remove_repo` | 레포 빼기(코드 상태도 지움 — 승인 창으로 확인) |
| `room_open_folder` | 요청한 사람 맥에서 사본 폴더를 Finder 로 열기 |
| `room_relink` / `room_reclone` | 요청한 사람 맥에서 원본을 다른 폴더로 다시 잇기 / 사본을 지우고 다시 받기 |

- 방 설정을 바꾸는 도구는 **승인 창**을 거친다(요청한 사람 맥). 멤버 누구의 요청이든 바꿀 수 있다(U10).
- 서버는 기준 브랜치가 원격에 있는지 앱이 확인한 값만 받는다(앱이 `ls-remote` 로 확인 뒤 보냄). 이름 규칙은 결정 38 의 검사 그대로.

### 3.2 자동 연결·자동 clone

- 방 레포가 생기거나 바뀌면 각자 앱이 원격 주소가 같은 레포를 찾아 쓴다(지금과 같음).
- 없으면 **자동으로 clone** 한다(`~/.claude-rooms/repos/<name>`). 진행은 레포 카드의 상태 점으로만(받는 중·정상·실패).
- 화면의 [레포 추가]·[폴더 고르기]·[clone 받기]·"…" 메뉴는 모두 없앤다(U12). 원본을 잘못 찾았거나 다시 받아야 하면 Claude 에게 말한다(방 도구 `room_relink`·`room_reclone` — 요청한 사람 맥에서만 동작).

### 3.3 실행 (공유 사본)

실행 전(요청한 맥):
1. 서버의 코드 상태를 받는다. 묶음이 있으면 `git fetch <bundle>` 로 스냅샷 커밋을 받아 사본을 그 상태로 맞춘다(아래 "맞추기").
2. 기준 브랜치를 fetch 한다. `origin/<기준>` 이 코드 상태의 `baseCommit` 보다 앞서 있으면 사본의 커밋들을 새 기준 위로 rebase 한다(커밋 안 한 변경은 잠시 치웠다 다시 얹음). 충돌이면 실행하지 않고 "기준 브랜치와 충돌해요"로 알린다(지금의 SYNC_CONFLICT).
3. Claude 실행(작업 폴더 = 사본).

실행 뒤(요청한 맥):
4. 사본의 상태를 스냅샷으로 만든다 — 임시 인덱스(`GIT_INDEX_FILE`)에 `git add -A` → `write-tree` → `commit-tree -p HEAD -p <이전 스냅샷>`(커밋 안 한 변경까지 담은 커밋, 첫째 부모 = 지금 HEAD, 둘째 부모 = 서버의 지금 스냅샷 — 있을 때만). 작업 폴더·실제 인덱스는 건드리지 않는다. 둘째 부모 덕분에 묶음에서 이전 스냅샷이 가진 파일 내용이 빠진다.
5. 스냅샷이 서버 코드 상태와 같으면 건너뛴다. 다르면 `git bundle create <file> <snapshot> ^<이전 스냅샷> ^<baseCommit>`(이전 스냅샷이 없으면 `^<baseCommit>` 만) → `PUT /rooms/:id/code-upload?requestId=` 로 흘려 올려 `uploadId` 를 받고, RUN_FINISH 에 `codeStates: [{ repoId, baseBranch, baseCommit, snapshot, prevSnapshot, uploadId }]` 로 붙인다. 서버는 레포마다 조각을 차례(seq)로 쌓고(prevSnapshot 이 null 이면 새로 시작), 기준 브랜치가 바뀌거나 push 로 승격되면 조각을 모두 지운다. 받는 맥은 마지막으로 맞춘 스냅샷 다음 조각들을 차례로 `git fetch` 한다(새 멤버는 처음부터). 조각이 100개를 넘으면 앱이 prevSnapshot 없이 한 번 통째로 올려 체인을 새로 시작한다. 2GB 를 넘으면 그 레포만 올리지 않고 채팅에 "변경이 너무 커서 공유하지 못했어요 · push 해 주세요".
6. 서버는 코드 상태를 바꾸고(트랜잭션 — 공유 파일·대화 원본과 함께) 방 멤버에게 `code.changed` 를 알린다.

맞추기(모든 맥, 실행 전 + `code.changed` 를 받을 때 곧바로):
- 스냅샷 S 를 받아 `git checkout --detach S^`(S 의 부모 = 커밋된 상태) 후 `git read-tree` 없이 `git checkout S -- .` 대신 **`git restore --source=S --worktree -- .`** 로 커밋 안 한 변경을 작업 폴더에 되살린다(인덱스는 비워 둠). 지워진 파일도 반영된다.
- 이 맥에서 그 방이 실행 중이면 맞추지 않고 실행이 끝난 뒤 맞춘다.
- 누가 사본을 Finder 로 직접 고쳤다면(U11): 맞추기 전에 이 맥 사본이 마지막으로 맞춘 상태와 다르면 맞추지 않고 레포 카드에 "이 맥에서 고친 내용이 있어요"를 표시한다. 그 사람의 다음 실행이 실행 전 1 단계에서 서버 상태를 먼저 받아 자기 변경과 합친 뒤(3-way, 충돌이면 멈춤) 4~6 에서 올린다.

- 맞추거나 올린 뒤 앱은 원본 레포에 이름표 `refs/rooms/<방 id>/<레포 id>` 를 그 스냅샷으로 갱신한다(사본은 원본의 git 데이터를 함께 쓰므로 원본에서도 바로 보인다). 원본의 작업 폴더·브랜치는 건드리지 않는다(U1). 공유 사본 내용을 내 로컬 브랜치로 가져가는 것은 사람이 직접(`git switch -c <브랜치> refs/rooms/…`, `git cherry-pick`, `git restore --source=…`) 하거나 채팅으로 시킬 때만(승인 창) 한다.

### 3.4 push ("push 해줘")

- Claude 안내문: 작업 단위로 나눠 커밋한다(`[키] feat|fix|refactor: 요약`, 결정 17). 작업 브랜치로 `git push -u origin HEAD:refs/heads/<작업 브랜치>`(없으면 기준 브랜치). 보호 브랜치(main·master·develop·production·release/*·hotfix/*)면 push 하지 않는다.
- push 가 끝나면 앱이 알아채서(실행 뒤 `ls-remote`) 방 레포의 **기준 브랜치 = 작업 브랜치**로 바꾸고 코드 상태의 `baseCommit` 을 push 한 커밋으로 바꾼다. 그 뒤 묶음은 push 뒤 변경만 담는다.

### 3.5 브랜치 바꾸기(결정 38 대체, U14)

- 사용자가 "develop 기준으로 하자", "작업 브랜치를 feature/X 로"라고 하면 Claude 가 `room_set_repo` 로 바꾼다(승인 창). 바뀌면 모두의 사본이 새 기준으로 맞춰지고 채팅에 한 줄.
- 기준 브랜치를 바꾸면 그 레포의 코드 상태는 비운다(새 기준 그대로에서 시작). 지금 사본에 커밋·push 안 한 변경이 있으면 Claude 가 바꾸기 전에 사용자에게 알리고 확인받는다(안내문).
- 결정 38 의 실행 끝 감지(`scanBranches`·`pendingBranches`·`rooms_branch_changes` 의 대기)는 없앤다.

## 4. 화면

- 레포 카드: `insight` 한 줄 + `release/15.7.0 → feature/NMRS-23055` 한 줄(작업 브랜치가 없으면 기준만) + 상태 점(정상·받는 중·충돌·실패). 마우스를 올리면 원격 주소·원본·사본 경로 툴팁. 버튼 없음(U12).
- 레포가 없을 때: "Claude에게 어떤 레포로 작업할지 말해 보세요" 한 줄.
- 채팅: 방 도구로 설정이 바뀌면 "insight를 release/15.7.0에서 feature/NMRS-23055로 작업해요" 한 줄. 사본이 바뀌면 diff 카드(지금과 같음).
- 멤버 탭의 레포 관련 연결 요약은 그대로.

## 5. 서버·데이터

- `room_repos`: `branch` → `base_branch`(기존 값 옮김), `work_branch` 추가(기존은 비어 있음), `origin_branch`(처음 정한 기준, U16) 추가.
- 새 테이블 `code_states(repo_id PK, base_commit, snapshot, size, updated_by, updated_at)`(최신 요약)와 `code_parts(repo_id, seq, prev_snapshot, snapshot, base_commit, size, created_at)`(증분 조각), 조각 파일은 `data/rooms/<방>/code/<repo_id>-<seq>.bundle`.
- 새 메시지: 방 도구용 `ROOM_REPO_SET`·`ROOM_REPO_REMOVE`(멤버 누구나, 실행 중 요청의 요청자만 — 실행과 묶어 검사), 알림 `CODE_CHANGED { roomId, repoId }`, 조각 목록 `GET /rooms/:id/code/:repoId`·조각 받기 `GET /rooms/:id/code/:repoId/:seq`(멤버만).
- 묶음 올리기 HTTP `PUT /rooms/:id/code-upload?requestId=`(실행 중 요청의 요청자만, 스트림으로 임시 파일 `code/.upload-*`, 2GB 상한, git bundle 머리 검사) → `uploadId`. RUN_FINISH 의 `codeStates` 가 `uploadId` 를 가리키면 그 파일을 `<repo_id>.bundle` 로 옮긴다. 서버 시작 때 남은 임시 파일은 지운다.
- RUN_FINISH 에 `promotedRepoIds`(push 로 작업 브랜치가 원격에 생긴 레포 → 기준 = 작업, 작업 = 비움).
- 방 삭제·레포 빼기 때 묶음 파일도 지운다. fork 는 코드 상태도 복사한다.

## 6. 검증

- 코어(Node, 임시 git 레포 + bare origin): 스냅샷 만들기(새 파일·삭제·커밋 안 한 변경 포함, 실제 인덱스 불변) / 묶음 → 다른 사본에 맞추기(커밋·미커밋 구분 유지) / 기준 브랜치가 앞서면 rebase, 충돌이면 멈춤 / 스냅샷이 같으면 안 올림 / push 뒤 기준 브랜치 = 작업 브랜치 / 직접 고친 사본은 맞추지 않음.
- 서버: 코드 상태 저장·교체·방송, 멤버만 묶음 받기, 방 도구 메시지 검사(요청자·이름·원격 존재), 레포 빼기·방 삭제 때 정리.
- 맥 두 대: A 가 시킨 변경이 B 사본에 곧바로 보이고, B 가 이어서 시키면 A 의 변경 위에서 일함 / "push 해줘"로 작업 브랜치가 원격에 생기고 나눠진 커밋 / 남이 기준 브랜치에 push 한 것이 다음 실행에 반영.
